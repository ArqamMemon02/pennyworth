## 2026-10-05 — Milestone 1: display stack + simulator
- **Graphics choice: LVGL 9.6 with its built-in SDL simulator.** Picked over LovyanGFX because LVGL ships an official SDL desktop backend (`lv_sdl_window_create`) out of the box — the simulator deliverable needs no custom wrapper — and the widget/timer/animation system LVGL already has is exactly what Milestones 2-5 need (day/night transitions, state-machine-driven sprites, a launcher). LovyanGFX is lighter and has great GC9A01 support, but has no desktop simulator story, so hitting "round mask + clock text in the simulator" would've meant writing that bridge by hand first. Heavier dependency, but it's the lazier path to everything the roadmap actually asks for.
- Config: copied LVGL's `lv_conf_template.h` into `include/lv_conf.h` (enabled via `LV_CONF_INCLUDE_SIMPLE`), flipped it on, enabled Montserrat 28 for the clock face, and made `LV_USE_SDL` conditional on a `PENNYWORTH_SIMULATOR` build flag so the ESP32 build doesn't need SDL headers.
- Hardware-agnostic UI code lives in `lib/pennyworth_ui/` — a single `pennyworth_ui_init()` that draws the round mask (visualizes the physical display's circular visible area) and a live clock label. Called identically from both entry points.
- Two entry points, selected per-env via `build_src_filter`: `src/main_native.cpp` (SDL window + mouse input, `lv_timer_handler()` loop) and `src/main_esp32.cpp` (Arduino `setup()`/`loop()`, LVGL display buffer in RAM, flush callback is a stub). The ESP32 side has no real panel driver yet — the board hasn't arrived and CLAUDE.md says never guess pins — so `flush_cb` just acks the buffer. Milestone 6 replaces that stub with a real GC9A01 driver once pins are verified into `include/board_pins.h`.
- Gotcha: PlatformIO's "native" platform build doesn't put the project's `include/` dir on the search path when compiling library sources (only the final app TU), so LVGL's own `lv_conf.h` lookup failed until `-Iinclude` was added explicitly to both envs' `build_flags`.
- Verified: `pio run -e native -t exec` opens an SDL window showing the round mask with a live `HH:MM:SS` clock (confirmed via screenshot). `pio run -e esp32-s3` builds clean too — 34.6% RAM, 16.5% flash.
- Next: Milestone 2 — day/night tone system with smooth time-based transitions, sun corner for day, twinkling stars + real moon phase for night (unit-tested against known dates).

## 2026-10-05 — Milestone 2: the world
- `lib/pennyworth_world/` — hardware-agnostic again, drawn as children of the round mask. `pennyworth_world_update()` is called from the existing 1s clock timer, no new timer needed.
- **Tone:** 9 keyframes across 24h (deep night → warm amber morning → bright day → warm evening → dim cool night → wrap), linearly interpolated per-channel on the fractional hour. Kept all keyframe colors mid-saturation on purpose — a near-white "bright day" or near-black "deep night" would wash out the white clock text, so brightness stays bounded even at the extremes.
- **Moon phase:** Conway's algorithm (`lib/pennyworth_world/moon_phase.cpp`) — a closed-form date formula, no lookup tables, per CLAUDE.md. Unit-tested in `test/test_moon_phase/` against 4 known new moons and 4 known full moons (2000-2024), via `pio test -e native`. Accurate to ~1 day in practice (verified by prototyping the formula in Python against the same reference dates before writing the C++).
- **Moon rendering:** two overlapping same-size discs (light "lit" + dark "shadow"), shadow offset horizontally by `(1-cos(2π·phase))/2 · diameter`, sign flipping at the half-cycle mark so waxing and waning mirror each other through the quarters. No image assets, no canvas — just two circle widgets.
- **Sun/stars/moon visibility** is a hard cut at the day/night boundary (6:30/18:00); only the background tone transitions continuously. Stars are 14 fixed-but-seeded dots, each with its own randomized infinite ping-pong opacity animation for twinkle.
- **Two real bugs found by actually screenshotting the simulator, not just checking it built:**
  1. `lv_obj_set_style_clip_corner()` on the round mask hid *everything* — including the dead-centered clock label — not just the square corners it was meant to crop. Root cause not chased down (LVGL 9.6 + SDL software renderer, possibly a known issue); the fix instead was to drop clipping entirely and size/position every element (moon's max shadow excursion included) with enough margin to stay geometrically inside the 120px-radius circle by construction. Cheaper on the ESP32 besides — no per-frame clip mask.
  2. Day/night visibility only updated *on change* (`is_day != s_is_day`), and `s_is_day`'s default (`true`) happened to match a boot during daytime, so the toggle silently never ran and night-only elements stayed visible under a blue sky. Fixed with an explicit `s_visibility_applied` latch so the very first `pennyworth_world_update()` call always sets visibility regardless of what the static default happens to be — a lesson for the state machine in Milestone 3 too: initialize explicitly, don't rely on a comparison against a guessed default.
- Verified both day and night visually (screenshots, including a temporary forced-hour build to exercise the day path) before committing. `pio run -e esp32-s3` still builds clean — 34.6% RAM, 16.8% flash.
- Next: Milestone 3 — original pixel art for Pennyworth (asleep/waking/awake/idle), state machine ASLEEP ↔ WAKING ↔ AWAKE ↔ SLEEPING driven by double-tap and timeout events.

## 2026-10-05 — Milestone 3 (art pipeline): sprites loading, state machine still to come
- User chose the AI-generation art pipeline over hand-drawing or procedural LVGL primitives. 4 sprites generated via Canva's `generate-image` (pixel-art prompt: orange tabby, round glasses, black suit/bow tie, per CLAUDE.md's character brief) + `remove-background` for alpha transparency: `pennyworth_asleep`, `pennyworth_waking`, `pennyworth_awake`, `pennyworth_awake_blink`. Downloaded as 200x200 RGBA PNGs (`assets/sprites/`) via the asset's signed thumbnail CDN URL from `get-assets` — there's no direct "download raw bytes" tool, so that URL (not the `canva.com/M/...` share link) is the actual path from a Canva MEDIA id to local bytes.
- **Embedding: LVGL's bundled lodepng runtime decoder, not a raw-bitmap converter.** `LV_USE_LODEPNG` flipped on in `include/lv_conf.h`; `tools/png_to_c.py` (new, ~50 lines) wraps each PNG's raw file bytes in a `uint8_t[]` + `lv_image_dsc_t{.header.cf = LV_COLOR_FORMAT_RAW_ALPHA, ...}`, following LVGL's own example (`lvgl/examples/libs/lodepng/img_wink_png.c`) — generated into `lib/pennyworth_sprites/pennyworth_sprites.c`. Skipped the official `LVGLImage.py` raw-bitmap converter: it'd save flash/RAM by pre-decoding to a native pixel format, but that's a real optimization pass against real constraints we don't have numbers for yet, not a Milestone-3 problem. Decoding PNG at runtime costs ESP32-S3 cycles+heap instead of flash, which is the right trade for now.
- **Real bug, found by actually looking at the simulator again:** the sprite didn't render — `decode_png_data: error 83: memory allocation failed`. LVGL's default built-in allocator (`LV_STDLIB_MALLOC_BUILTIN`) uses a fixed 64KB pool (`LV_MEM_SIZE`), and decoding one 200x200 RGBA PNG needs a 160KB output buffer alone — 2.5x the whole pool, so it always failed, silently (no warning without `LV_USE_LOG`, which is off by default). Fixed by switching `LV_USE_STDLIB_MALLOC` to `LV_STDLIB_CLIB` — real `malloc`/`free` instead of a fixed pool. This also fits the hardware better: ESP32-S3 Arduino's `malloc` already spans internal RAM + PSRAM via `heap_caps`, so there's no good fixed pool size to pick anyway. (Side effect: ESP32 build's *static* RAM usage reported by the linker dropped from 34.6% to 14.6%, since LVGL's pool is no longer reserved BSS — real usage now happens on the heap at decode time instead, which the linker can't see.)
- Wired minimally into `lib/pennyworth_ui/pennyworth_ui.cpp`: a static `pennyworth_awake` image, scaled to 43% and nudged below the clock (which moved up to make room). No state machine yet — ASLEEP/WAKING/AWAKE/SLEEPING transitions and double-tap wiring are Milestone 3's other half + Milestone 4, deliberately not touched here. Idle-life touches from CLAUDE.md §3 (ear twitch, tail flick, slow blink animation beyond the static blink-frame swap) are also deferred to when the state machine exists to drive them — no point animating a sprite that can't yet change state.
- Verified: both envs build clean (`esp32-s3`: 14.6% RAM / 18.4% flash — the +57KB flash over Milestone 2 is the 4 embedded PNGs, ~35KB each before compression headroom). Screenshotted the simulator and confirmed the cat renders correctly, fully legible, and stays inside the round mask at every zoom level checked. (One screenshot showed large ghosted background text through the window — traced to Hyprland's inactive-window-opacity compositor rule letting whatever's behind bleed through an unfocused headless window, not an app bug; a normal-contrast capture and a focused window are both clean.)
- Next: the actual Milestone 3 state machine (ASLEEP ↔ WAKING ↔ AWAKE ↔ SLEEPING) and Milestone 4's double-tap-driven transitions, which is when all 4 sprites actually get used instead of just `pennyworth_awake`.

## 2026-10-05 — Milestone 3 (state machine): all 4 sprites live
- `lib/pennyworth_state/` — `pennyworth_state_init()`/`_wake_event()`/`_tick()`. ASLEEP → (wake event) → WAKING → (700ms) → AWAKE → (8s inactivity) → SLEEPING → (500ms) → ASLEEP. A tap while AWAKE resets the inactivity clock instead of re-triggering WAKING; taps mid-transition (WAKING/SLEEPING) are ignored rather than queued — simplest thing that can't get the state machine into a weird half-entered state.
- `enter_state()` always sets `s_state_entered_ms = lv_tick_get()` and swaps the sprite on entry, so every transition is driven by "how long have I been in this state" rather than anything that can desync — same lesson Milestone 2's visibility-latch bug taught, applied up front this time instead of found by a bug.
- **Wake trigger, for now: a tap/click on the round mask.** CLAUDE.md §5 already specs "touchscreen tap may also wake as a fallback," so this isn't scope creep ahead of Milestone 4 — it's that one fallback path, pulled forward because the state machine needs *some* input to demo against, and double-tap-via-IMU is real hardware work that belongs in Milestone 4 proper.
- **Idle life, partial:** slow blink implemented (random 2.5-5s interval, 150ms hold, swaps to `pennyworth_awake_blink` and back) since it's just a second sprite swap. Ear twitch and tail flick from CLAUDE.md §3 are **not** implemented — they'd need dedicated art frames we don't have, and animating a feature the character doesn't have art for would mean faking it with LVGL transforms (scale/skew) on sub-regions of a single flat sprite, which is a lot of fiddly code for a "subtle, not busy" effect. Deferred until there's a reason to invest in part-based art (sprite sheet with separate ear/tail layers) rather than one flat image per pose.
- **SLEEPING reuses the `waking` sprite** (sitting-up pose, played as "lying back down") rather than a 5th dedicated frame — same silhouette works in both directions, and generating a near-duplicate sprite for one 500ms transition wasn't worth it.
- Verified via debug prints (not screenshot-timing guesses, which I misread once — see below) with a temporarily shortened 1.5s timeout and an auto-wake-after-1s debug hook in `main_native.cpp`: `t=79 ASLEEP → t=1091 WAKING → t=1840 AWAKE → t=3368 SLEEPING → t=3898 ASLEEP`, matching the coded 700/1500/500ms durations to within one 50ms tick. All debug code and the shortened timeout were reverted before committing (diff confirmed clean).
- Gotcha for next time: a screenshot taken mid-transition between two sitting poses (`waking` vs `awake`) is genuinely hard to eyeball correctly at small size — I misjudged one as "already awake" when the debug log proved it was still mid-WAKING. Trust timestamped logs over a quick visual read when two frames are this similar.
- Verified both day and night still render correctly with the sprite + state machine layered in; `pio test -e native` (moon phase) still passes. `esp32-s3`: 14.6% RAM / 21.9% flash.
- Next: Milestone 4 — real double-tap detection from IMU data (simulated via a key press on desktop), sleep/wake power logic that plugs into ESP32 deep sleep, and state persistence to flash (file-backed in the simulator).

## 2026-10-05 — Milestone 4: input + power logic
- **Double-tap detection: `lib/pennyworth_input/double_tap.{h,cpp}`**, deliberately pure (no LVGL, no hardware — just `double_tap_feed(detector, now_ms) -> bool`). Two taps within 400ms confirm; a lone tap, or two taps further apart, don't. Unit-tested (`test/test_double_tap/`, 4 cases including "triple tap confirms once, not twice" — the detector resets on confirm rather than staying armed, so it can't chain). `pennyworth_input.{h,cpp}` is the thin glue layer: `pennyworth_input_raw_tap()` feeds the detector and calls `pennyworth_state_wake_event()` on confirm — the one function both the simulator and (eventually) the real IMU call.
- **Simulated input: space bar on desktop**, per CLAUDE.md's own suggestion. Implemented as `SDL_GetKeyboardState` polling (reads live key state, a side effect of the SDL event pump LVGL's own driver already runs) rather than our own `SDL_PollEvent` loop, which would race LVGL's driver for the same event queue — found this while reasoning through it, not by hitting the bug. On ESP32, `main_esp32.cpp`'s `loop()` just carries a TODO for Milestone 6: call the same `pennyworth_input_raw_tap()` from real QMI8658 accel-spike detection once `board_pins.h` exists. Same stub-now/fill-in-at-hardware-bringup pattern as the display flush callback from Milestone 1.
- **Two wake paths now, matching CLAUDE.md §5 exactly:** a touchscreen tap (Milestone 3's click handler, unchanged) wakes directly, no double-tap gate — a deliberate single touch is real signal. The new double-tap path goes through the detector so accidental pendant bumps (which are single impulses) get rejected.
- **Power: `lib/pennyworth_power/`**, a 2-function interface (`enter_sleep`/`enter_wake`) hooked into `pennyworth_state.cpp`'s `enter_state()`. Both are no-ops on both platforms right now — the simulator has no real sleep state to enter, and the ESP32 side can't configure `esp_sleep_enable_ext0_wakeup()` on the IMU interrupt pin without knowing which GPIO that is, which needs the board. The point of building this now instead of at Milestone 6 is the call sites: the state machine already invokes power transitions at exactly the right moments, so Milestone 6 is "fill in two function bodies," not "find every place sleep should happen."
- **Persistence: `lib/pennyworth_storage/`**, file-backed on the simulator (`pennyworth_state.dat`, gitignored — a magic-number-prefixed struct, regenerated from defaults if missing or stale) and `Preferences` (ESP32 Arduino's NVS wrapper, already available, no new dependency) on hardware. Only field so far is `sleep_timeout_s` — the AWAKE inactivity timeout, which used to be a `#define` and is now loaded at `pennyworth_state_init()` time instead, so Milestone 5's launcher has something real to persist when it adds a settings screen. Didn't add a `brightness` field yet since nothing reads it — YAGNI until the launcher needs it.
- Verified everything with debug prints rather than fighting this sandbox's flaky GUI-input-injection story (`wtype`/`hyprctl focuswindow` kept dying silently mid-script): an isolated tap at t=590ms logged `confirmed=0`, two taps 200ms apart at t=2108/2306ms logged `confirmed=0` then `confirmed=1` and correctly fired `enter_state=WAKING`. Persistence verified by inspecting the written file directly (`od -A x -t x1z`) — magic bytes + `sleep_timeout_s=8` (the default), confirming the load-writes-defaults-when-missing path. All debug code reverted before committing (diffs reviewed clean).
- Both envs build clean: `esp32-s3` 14.6% RAM / 22.1% flash (+0.2% flash over Milestone 3 — this stuff is cheap).
- Next: Milestone 5 — minimal custom launcher reachable from AWAKE, with brightness and sleep-timeout settings (finally giving `pennyworth_storage` a second field and a UI to write it from).

## 2026-10-05 — Milestone 5: launcher
- `lib/pennyworth_launcher/` — a gear icon (`LV_SYMBOL_SETTINGS`), visible only while `pennyworth_state_get() == PENNYWORTH_AWAKE`, opens a small settings panel with two `lv_slider`s: brightness (10-100%) and sleep timeout (3-30s). Both apply live (brightness redraws a dimming overlay immediately, timeout calls the new `pennyworth_state_set_awake_timeout_ms()` setter so a change takes effect on the AWAKE period already in progress) and persist on `LV_EVENT_RELEASED` rather than every drag tick — no reason to hammer flash/NVS while a slider is mid-drag.
- `pennyworth_settings_t` gained a `brightness` field (storage struct magic bumped `PNW1`→`PNW2` so a stale pre-Milestone-5 file gets detected and regenerated with defaults rather than misread). Brightness has no real backlight PWM yet — same story as the IMU and display driver, needs a verified pin from Milestone 6 — but the simulator fakes it convincingly with a black overlay `lv_obj` layered on top of everything (world, sprite, clock), created last in `pennyworth_ui_init()` specifically so dimming affects the whole scene at once. The gear icon and settings panel are created after the overlay, so they stay fully legible even at low brightness — adjusting settings shouldn't require first turning the brightness back up.
- Geometry: panel is 170×150 centered, undersized enough (farthest corner ~113px from center) to stay inside the 120px round boundary with plain square corners — same containment approach as Milestone 2's moon, no clipping trick needed.
- Verified with the same debug-hook technique as Milestone 4 (temporary exported `_debug_force_open()`/`_debug_set_brightness()` functions called from a one-shot timer in `main_native.cpp`, screenshotted, then fully deleted before commit — diff reviewed clean): confirmed the gear icon is hidden while ASLEEP, appears once AWAKE, the panel renders correctly with live slider values, and setting brightness to 20% visibly dims the whole display while the gear icon stays bright.

## 2026-10-05 — Milestone 6 (prep only): hardware bring-up checklist
- Wrote `docs/HARDWARE_BRINGUP.md` — the procedure for when the board arrives, not pin numbers committed to code yet.
- Researched the board's pins (Waveshare wiki + community demo repos) to make real bring-up faster later, and hit exactly the failure mode CLAUDE.md's "never guess pin numbers" rule warns about: two sources disagree on LCD backlight (GPIO2 vs GPIO40) and reset (GPIO14 vs GPIO12), and one source is internally inconsistent (MISO=12 contradicts its own reset=12). DC/CS/SCLK/MOSI and the shared touch+IMU I2C bus (GPIO6/7) were consistent everywhere, so those are reasonably trustworthy; the conflicting ones are documented as an open question in the bring-up doc, not resolved by guessing. **Did not create `include/board_pins.h`** — that only gets written once the conflict is resolved against the real schematic/demo code with the board in hand.

Everything else in `docs/HARDWARE_BRINGUP.md` (display driver swap, touch indev, IMU accel-spike detection, power syscalls) has its exact insertion point already marked with TODOs in the code from Milestones 1-4 — bring-up is "fill in N stubs," not "figure out where this goes."
